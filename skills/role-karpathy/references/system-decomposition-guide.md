## 1. 拆解五问

对任何一个待验证对象（一个方案、一个组织流程、一个模型、一段业务流程）依次问五个问题。任何一问答不出来，说明拆解还没完成，而不是说明问题不可拆。

**问一：边界在哪里。**
系统从哪开始、到哪结束？哪些东西被明确排除在外？排除项必须写出来，因为大多数争论其实是边界之争——两人在讨论不同的系统。做法：写一句「本模块不负责 X、Y」，并确认对方接受这个排除。

**问二：输入与输出是什么。**
输入：进入模块的数据、资源、指令，各自的格式、量级、到达频率。输出：离开模块的东西，包含成功输出与失败输出（失败也必须是一种明确的输出形态，而不是「什么都不发生」）。判据：任意两个人都能根据这份描述，独立判断某次运行属于哪一类输出。

**问三：状态在哪里。**
系统里有没有跨时间保存的东西（缓存、账本、已训练参数、用户已填写的内容、组织里的既有承诺）？状态是最容易被漏掉的模块边界，也是可复现性最大的敌人。做法：列出所有持久化对象，标注它的生命周期与谁能改写它。

**问四：失败模式有哪些。**
至少列出三类：输入异常（数据缺失、格式不符、量级突变）、内部异常（超时、部分成功、重试导致重复）、外部依赖失败（上游不返回、下游拒绝）。每个失败模式要写清「如何被发现」和「发现后如何回退」。没有回退方案的失败模式等于没有设计。

**问五：观测点在哪里。**
在哪些位置可以观测到信号？观测本身要不要付出代价（延迟、成本、打扰用户、改变被测对象的行为）？如果只能观测最终结果，就必须承认：中间环节的推断都是不可验证的，只能标 `unverified`。

**五问的输出格式**（可直接填入发言的 `evidence` 或写成附注）：

```
对象：<被拆解的系统>
边界：负责 …… ；不负责 ……
模块：
  1) <名称> | 输入：…… | 输出（含失败输出）：…… | 成功判据：……
  2) ……
接口假设：<见第 2 节>
状态：<持久化对象及其生命周期>
失败模式：<输入异常 / 内部异常 / 外部依赖失败，各自的发现方式与回退方案>
观测点：<位置 + 观测代价 + 只能间接推断的部分>
当前未验证项：<依赖链，见第 4 节与第 3 节>
```

填写时若某一栏反复写不出来，通常不是描述能力问题，而是这个系统还没有被想清楚——此时应当先承认不确定，而不是用更漂亮的措辞填补空白。

## 2. 接口假设清单模板

接口假设写错是最常见的失败源。模板如下，每个模块交界处填一份：

```
接口：<模块A> -> <模块B>
传递内容：<字段/对象/事件>
格式与量级：<结构、单位、典型规模、峰值>
时序假设：<同步/异步、顺序、延迟上限、重复投递是否可能>
一致性假设：<A 认为已提交的数据，B 多久后一定能读到>
错误传递：<A 失败时如何告知 B；B 失败时 A 是否重试；重试是否幂等>
隐藏前提：
  - A 的输出分布与 B 训练/设计时假设的分布一致
  - 双方对同一字段的口径一致（例如「活跃用户」的定义）
  - 没有人会绕过 A 直接写 B 的输入
该假设被打破时的表现：<症状>
验证该假设的最小实验：<见第 4 节模板>
```

填写纪律：`隐藏前提` 一栏必须至少写两条，写不出来通常说明对接口的理解停留在口头协议层面。

## 3. 可复现性检查表

对每条论断逐项过一遍，任一项缺失即该论断不能作为已确立事实使用，只能标 `unverified`。

**数据来源**：原始数据在哪、谁采集、什么口径、时间范围、样本量与筛选条件。是原始数据还是二手转述？转述过程中做过哪些加工（清洗、去重、截断、补全）？

**随机性**：是否存在随机初始化、随机采样、随机分流、人工挑选？种子、重复次数、方差是否报告？单次结果是否被当作稳定结论？多次运行的波动范围是多少？

**环境**：运行环境的版本、依赖、硬件、并发度、参数配置。同一段描述在另一台机器上能否得到同类结果？如果答案依赖某个未公开的调参过程，必须写明这一点。

**评测集**：评测集怎么构造、与训练/设计过程是否重叠、由谁标注、标注一致性如何。评测集是否被反复使用到已经间接过拟合？是否保留了一个从未用于决策的留出集？

**泄漏风险**：未来信息是否通过特征、缓存、聚合统计或人工先验进入了决策？评测阶段是否用到了不可在生产中获取的信息？对照口径：把「如果去掉这个特征/这块信息，结论是否还成立」当作标准问句。

## 4. baseline 与消融实验设计模板

**最简 baseline**：用最少组件与最少假设跑通完整链路，目标是先产生一个可观测结果，而不是先得到好结果。记录它的绝对表现，作为后续一切改动的参照点。若连 baseline 都跑不通，说明链路本身有结构性缺陷，此时增加复杂度只会掩盖问题。

**复杂度清单**：每增加一个组件、一层模型、一条规则、一个流程环节，都填一行：

```
改动：<增加/修改了什么>
预期改善：<哪个指标、多少幅度、可测量的口径>
成本：<延迟、复杂度、维护、失败面、可解释性损失>
边际收益判定：正 / 零 / 负 / 未知（未知即待删）
若为零收益，删除它需要什么：<说明>
```

「待删」项不得静默留在方案里当作必要组件；若因为时间或依赖无法立即删除，必须显式标注它是已知的冗余。

**消融设计**：对每个声称有贡献的组件，做一次「只去掉它」的实验，其余保持不变。同时做一次「只留它」的实验以观察它单独能否工作。两次结果不一致时，通常说明组件之间存在耦合，需要回到第 2 节检查接口假设。

**判定纪律**：实验前先写下「什么结果会让我放弃这个改动」，事后不允许事后修改判据。若因客观原因无法做实验，必须明确写出「这是未验证的判断」，而不是用推理链代替实验结论。

## 5. 古德哈特与指标代理效应

**核心机制（抽象场景）**：某个团队需要一个数字来衡量「系统是否变好」，于是选定一个容易测量的代理指标。指标被写入目标后，所有参与者开始优化这个数字本身。一段时间后数字持续上升，而它原本代理的真实目标没有改善甚至恶化——因为代理与真实目标之间的相关性只在小范围内成立，超出范围就断裂。

**三类典型断裂**：

1. **压力转移**：把成本推给未被测量的部分。例如把耗时任务从被测路径挪到未被测路径，指标变好而总成本不变。
2. **目标替换**：可测量的下限变成天花板。例如「最低覆盖率」被当成「刚好达标即可」，覆盖率数字漂亮而质量下降。
3. **样本迎合**：让被测样本变得更容易预测，而不是让系统变得更强。例如反复调参直到在固定评测集上表现最好。

**防作弊与防泄漏做法**：

- 至少保留一个与主指标机制不同的第二指标，两者必须同时改善才算有效；两者背离时应先怀疑主指标。
- 把「查询次数、样本数量、人工介入量、成本」作为约束一起记录，防止通过增加未计量资源换取指标。
- 评测集与决策流程分离：用于决策的数据与用于汇报的数据不重叠；留出集在最终确认前不参与任何选择。
- 定期做「反向抽样」：主动查看指标最差的那部分样本，而不是只看榜单整体的平均值。
- 对指标的极限形态做思想实验：如果它被优化到 100%，系统会变成什么样子？如果答案是荒谬的，就必须限制它的权重或更换指标。
- 所有指标口径变动（定义、口径、采集方式）必须显式记录，因为口径变化常被误读为真实变化。

**第二个抽象场景**：一个流程用「平均处理时长」衡量效率。参与者把简单任务优先处理、把复杂任务排到队尾，平均值持续下降，而客户感受到的等待时间上升——因为被删掉的是长尾样本。

- 处理方式：报告分位数（例如最慢的 5% 有多慢），而不只报平均值；把被推迟的任务数量作为约束一起记录。
- 一般化结论：任何「平均值型」指标都可能通过丢弃长尾来改善，因此至少需要一个长尾指标与之配对。

**判断自己是否正在被指标牵引的自检问句**：

1. 如果这个数字下降而真实状况变差，我需要多久才能发现？
2. 这个数字变好，会不会因为我少做了某件没被测量的事？
3. 我上一次查看最差样本是什么时候？

## 6. 「看起来对」的常见陷阱

- **过拟合**：结论只在被反复使用的那一小撮样本上成立。识别特征：换一批样本结论就散；对参数微小变动极度敏感；多个「最优」选择之间差异小于波动范围。
- **选择性报告**：只报成功的实验、只报有利的区间、只报最早的几轮结果。识别特征：缺少失败实验的记录；成功与失败的实验条件看起来不一致；只有结论没有操作日志。
- **幸存者偏差**：样本只包含活下来的个体，看不到已经消失的同类。识别特征：样本通过某个事后的门槛筛出（今天还存在的公司、还没被删掉的账号、还在维护的项目）。
- **评测集污染**：评测数据以间接方式进入了设计过程。识别特征：某些样本表现异常突出；换用全新评测集后指标明显下降；模型能复述评测集的细节。
- **把相关性当因果**：观察到两个量一起变化就断言其中一个导致另一个。识别特征：没有说明干预方式；没有排除共同原因；没有给出反事实（如果不做 X 会怎样）。
- **把叙述当证据**：一个顺畅的故事被当成机制证明。识别特征：故事里的每一步都合理，但没有任何一步被单独观测过。
- **把缺席当否定**：因为没找到证据就断言不存在。识别特征：把「我没查到」写成「已证实没有」，且未说明检索范围。
- **口径漂移**：用同一个词讨论不同的量，或中途悄悄换了定义。识别特征：讨论到一半指标上升但没人说得清是真实变化还是口径变化。

## 7. 哪些问题不该用这套方法

系统分解与可复现性检查是强有力的，但有明确的适用范围。对下面几类问题使用这套方法，得到的不是更严谨的结论，而是被扭曲的问题。

**纯价值判断**：这类问题的答案取决于你重视什么，而不取决于数据。「这件事值不值得做」「这种体验算不算好」「应该优先谁的利益」属于此类。它们可以被澄清、可以被列出取舍，但不能被实验证伪。正确做法是承认它属于价值判断并显式标注，而不是硬造一个指标来伪装成事实。

**一次性不可逆决策**：无法重复、无法并行的决策（关停一条业务线、公开承诺一个方向、涉及人身安全的选择）缺少可复现性的前提，因为不存在第二次运行。对这类问题，本手册能提供的只有「失败模式清单」和「回退方案设计」，不能提供统计意义上的验证。

**小样本且高方差的探索**：当可观测样本只有几个，任何指标都在噪音范围内。此时正确的做法是记录直接观察与直觉，并在证据强度上如实标低（例如使用 `intuition` 并降低 `confidence`），而不是套上指标外衣。

**历史反事实与不可干预的问题**：若历史不可重演、也无法做对照，就不存在可复现实验。可以做的只是机制推演与多方证据交叉，输出时必须标为 `mechanism` 而非 `empirical`。

**紧急且代价不对称的场景**：当不作为的代价远大于误作为的代价、且时间窗口极短时，先跑通 baseline 的顺序会让决策成本高于收益。此时应先做最坏情况分析，再决定是否需要完整验证，并在发言中显式说明「这里我放弃了可复现性要求，理由是时间不可逆」。

判断方法很简单：先问「需要一个什么观察才能改变我的答案」。如果无论观察到什么，答案都不会改变，那它就不是可验证问题；如果需要一个无法获取的观察，那它当前就不是可验证问题。两种情况都应如实标注，而不是绕开。

**遇到这类问题时的替代做法**（不是放弃严谨，而是换工具）：

- 纯价值判断：把各方的价值排序显式写出来，标注哪一步是不可通约的取舍，交给决策者，不用证据强度伪装。
- 一次性不可逆决策：列出最坏情况与不可逆点，设计可回退的中间步骤（把一次大赌注拆成几个小赌注），这是本手册唯一能提供的部分。
- 小样本探索：记录直接观察的原话与场景，标明样本量，用较低 `confidence` 表达，并说明「若样本扩大后结论可能怎样变化」。
- 无法干预的历史问题：区分「已确认的事实」「机制推演」「我的判断」三层，分别对应 `empirical`、`mechanism`、`value_judgment`，绝不混写。

无论采用哪种替代做法，都必须在发言中显式说明「此处不使用系统分解方法，原因是 ……」。默认套用工具比不用工具更容易出错。
