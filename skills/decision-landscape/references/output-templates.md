# 决策景观 · 报告模板与写法手册

> **示例数据声明**：本文出现的议题、事件与发言均为**虚构示例数据**，仅用于演示报告结构；场景一律抽象化（"某团队""某项目"），
> 不含名人原话，也不含真实公司未公开事件。示例中的编号（`H`/`D`/`G`/`F`/`C`）与 claim id 只是占位符，实际编号由元认知层与状态文件给出。

## 1. 完整报告模板（六板块骨架）

```markdown
# 决策景观报告 — <topic>

- 会话：<session_id>　轮次：<round>/<max_rounds>　阶段：<phase>　模式：<mode>
- 收敛建议：<convergence.recommendation>　根因触及：<convergence.root_cause_reached>
- 说明：本报告为结构聚合结果；带"待复核"的条目属语义判断项；结论性文字均可追溯到 claim id 或 H/D/G/F/C

### 一、共识区（consensus_candidates）
| 结论 | 支持角色 | 强度 | 备注（剔除的漂移者／待复核） |
|---|---|---|---|
| ……（来源：M1-1, K2-1） | musk, karpathy | weak | 结构计数，非语义判定 |
无候选时写：本场讨论未产生满足 --min-support 的共识候选。

### 二、分歧区（divergence_map）
#### [D1] <议题>　类型：事实｜价值｜术语｜伪分歧
- 各方立场：……
- 消解路径：……
- 关联信息缺口：G1（事实分歧必须给出 G 编号）
- 状态：open

### 三、隐性假设清单（hidden_assumption_list）
- [H1] 内容：……　涉及角色：……　若被挑战可能改变：……
- 状态：open　是否已被回应：否（单列，待下一轮挑战）

### 四、决策建议（confidence_weighted_advice）
#### 高置信度（high）　#### 中等（medium）　#### 需补充信息（needs_info）
每条格式：建议内容（来源：claim id 或编号；依据角色自报 confidence）

### 五、信息缺口清单（information_gaps）
| 编号 | 缺失信息 | 补上后可能翻转的判断 | 获取成本 | 状态 |
|---|---|---|---|---|

### 六、少数派观点保护（minority_views）
#### [角色] <claim id>：<claim 原文>
- 证据：……
- 收到的质疑：C1（质疑者=……）：……
- 状态：refuted=false —— 未被有效反驳，完整保留
```

六板块顺序固定：共识 → 分歧 → 隐性假设 → 建议 → 缺口 → 少数派。
**不按轮次排列**：读者要知道的是"现在能定什么"，不是"谁在第几轮说了什么"。

## 2. 逐板块的合格 / 不合格对照

### 2.1 共识区
- 合格：`| 季度评审的成本下界高于年度评审（来源：M1-1、K2-1） | musk、karpathy | weak | 结构计数，非语义判定；恰好 2 人表态 |`
- 不合格："大家一致认为季度评审值得推进。"
- 差在哪：没有支持者名单、没有 `strength`、没有声明这是表态计数；2 人表态不能写"大家"。

### 2.2 分歧区
- 合格：`[D1] 评审频次是否影响评审深度　类型：事实｜各方立场：一方认为频次与发现问题数正相关，一方认为频次提高会稀释单次深度｜消解路径：需要"评审深度"的可比指标｜关联信息缺口：G1｜状态：open`
- 不合格："双方各有道理，建议综合考虑。"
- 差在哪：类型缺失导致处置方式无从选择；"综合考虑"不是消解路径，只是把分歧原样退回给读者。

### 2.3 隐性假设清单
- 合格：`[H1] 内容：评审的价值只能用"发现问题的数量"衡量｜涉及角色：全部｜若被挑战可能改变：焦点会从"几次评审合适"转向"用什么衡量评审有效"｜状态：open｜已被回应：否`
- 不合格："[H1] 评审频次问题。该假设已被讨论解决。"
- 差在哪：假设内容没写清（是"数量口径"还是"频次"？）；把 `status: open` 的条目说成已解决。

### 2.4 决策建议
- 合格：`在补齐 G1（评审深度的可比指标）前不建议改动频次；可先做小范围试点并记录指标。（来源：D1、G1；自报 confidence=55 → medium）`
- 不合格："建议加强评审机制建设，提升整体效率。"
- 差在哪：无来源编号、无可执行动作、无置信度档位，读者无法判断这句话来自哪条讨论。

### 2.5 信息缺口清单
- 合格：`| G1 | 近两年每次评审的实际工时与产出记录 | 若单次工时随频次上升而下降，则"频次提高稀释深度"可能成立 | low（现有记录可导出） | open |`
- 不合格：`| G1 | 更多数据 | 有助于更全面的判断 | — | open |`
- 差在哪：写不出"补上后可能翻转哪条判断"的是好奇而不是缺口；成本留空则无法判断该不该补。

### 2.6 少数派观点保护
- 合格：见第 4 节的固定格式。不合格："另有一位成员持不同意见，但多数人认为可以忽略。"
- 差在哪：把一条完整主张压缩成"有人反对"，并用多数票处置了未被有效反驳的观点。

## 3. 决策建议的三种写法

置信度取自 `positions[role].confidence`（**角色自报**，不是系统测量值），区间口径见 SKILL.md。

### 3.1 high（自报 ≥ 70）

```
- 按 K1 的模块拆分先做一次可独立验证的试点（来源：K1-1；自报 confidence=75）
```

纪律：可以写"建议优先执行"，但不得写"已验证""已确认可行"——本层没有执行任何验证。

### 3.2 medium（40–69）

```
- 在"单次评审深度不下降"这一前提成立时，可以试点季度评审（来源：M1-1；自报 confidence=60）
```

纪律：必须带限定条件，且限定条件要写成**可检验的前提**，不能写成"视情况而定"。

### 3.3 needs_info（< 40，或依赖未闭环的缺口）

```
- 待补 G1（评审深度可比指标）后再判断是否调整频次；在此之前不给出倾向性结论（来源：G1）
```

纪律：只写"待补充信息后再判断"。把低置信度建议包装成结论，是这份报告最容易发生的越界。

### 3.4 三条通用措辞纪律

1. 每条建议都要有来源编号；写不出来源的建议，说明它来自报告作者而不是讨论。
2. 一条建议涉及多个角色时取**最低**自报置信度，不做加权平均、不合成"综合置信度"。
3. 不得把角色原话直接搬成建议句：原话是证据，建议是加工后的动作，两者必须可区分。

## 4. 少数派观点段落的固定格式

每条 `refuted: false` 的少数派观点，按下列四行输出，缺一行即为不合格：

```markdown
#### [<角色>] <claim id>：<claim 原文，不改写、不缩写>
- 证据：<evidence 要点；若 basis=analogy 或 intuition，必须原样标注该论据类型>
- 收到的质疑：<C 编号>（质疑者=<角色>，指向=<claim id>）：<质疑内容原文>
- 状态：refuted=false —— 未被有效反驳，完整保留
```

建议再补一行边界说明：`未被反驳不等于成立，只表示现有讨论没有给出足以推翻它的理由。`

三个易犯错误：

1. **合并同类项**：把两条不同主张合成一段"少数意见"——它们论据不同，合并等于篡改。
2. **降格为脚注**：放进文末"其他"栏，与主线建议割裂；少数派观点应与共识条目同处报告主体。
3. **追加反驳**：报告作者替多数派补一句反驳，把 `refuted: false` 事实上变成 `true`。

## 5. 一页纸版与完整版的取舍

| 读者与场景 | 用哪一版 | 理由 |
|---|---|---|
| 只想知道"能不能拍板、下一步做什么" | 一页纸版 | 完整版的编号与依据对决策速度是噪声 |
| 要复核结论、对外引用、追问来源 | 完整版 | 需要逐条追溯 claim id 与 H/D/G/F/C |
| 存在 `refuted: false` 的少数派观点 | 完整版（或一页纸版附少数派段） | 少数派观点不允许被摘要吞掉 |
| 存在事实分歧且缺口未闭环 | 完整版 | 读者需要看到"缺什么、可能翻转什么" |

一页纸版骨架（控制在 300 字内）：

```
结论：能定的、不能定的各一句
下一步：1–3 条动作（带来源编号）
最大风险：1 条（优先写价值分歧或未闭环缺口）
少数派：1 条（角色 + claim id + 一句话原文要点）
```

铁律：**版面压缩不能压掉不确定性**。宁可一页纸版长一点，也不要把 `needs_info` 写成 `high`。

## 6. 常见坏报告清单

| 坏写法 | 为什么坏 | 改法 |
|---|---|---|
| 按轮次拼接发言（"第一轮 A 说……第二轮 B 说……"） | 时间线掩盖了"哪些是共识、哪些是分歧" | 改按六板块分区，来源用编号标注 |
| 用"大家一致认为"掩盖分歧 | 抹掉支持者名单与强度，制造不存在的共识 | 写清支持者与强度，注明是结构计数 |
| 把 value 分歧写成待调研事项 | 价值分歧补再多数据也不会收敛 | 显式声明不可调和，改问"各自在什么条件下成立" |
| 把 fact 分歧写成不可调和 | 明明可靠一条数据解决，却让读者以为必须妥协 | 补 `G`，写清缺失信息与可能翻转的判断 |
| 少数派观点被压成"另有不同意见" | 未被反驳的观点就此消失 | 按第 4 节固定格式完整保留论证 |
| 把 `compliance_drift_count ≥ 1` 的角色算作有效支持 | 共识强度被无证据的改口抬高 | 剔除该角色后重新计数，必要时降档 |
| 出现 ≥3 个角色漂移却仍报告"共识形成" | 这是假共识的典型信号 | 显式写出"当前共识可能是假共识" |
| 把脚本 `check` 通过当成语义结论 | 脚本只数结构，不判断内容对错 | 写明 `needs_judgment` 条目并完成复核 |
| 写"已达成共识""已验证""已挖到根本" | 断言了本层没有执行的动作 | 改成"候选""需复核""若补上 X 则判断可能改变" |
| 报告里自造 `H`/`D`/`G`/`F` 编号 | 编号只能由元认知层产生，自造会破坏可追溯性 | 回元认知层登记，或省略该判断 |
| 给出一个全篇"综合置信度" | 多人自报值平均成的人造数字，不可追溯 | 按 high/medium/needs_info 分档逐条呈现 |
| 只报结论不报边界 | 读者会以为讨论可以代替验证 | 结尾保留边界声明：不做语义判定、不保证跳出底座模型自身的偏见 |

## 7. 落笔前的快速核对

1. 讨论确实已关闭（`phase = closed` 或 `convergence.recommendation = close`）？
2. 每条共识都有支持者名单与 `strength`，且已剔除漂移角色的支持？
3. 每条 `D` 都有类型与消解路径，事实分歧都挂了 `G`？
4. 每条 `H` 都写了内容与"若被挑战可能改变什么"？
5. 每条建议都有来源编号与置信度档位，低置信度没有被写成结论？
6. 所有 `refuted: false` 的少数派观点都按固定格式完整出现？
7. 全篇是否出现"已达成共识""已验证""已挖到根本"这类未执行动作的断言？
