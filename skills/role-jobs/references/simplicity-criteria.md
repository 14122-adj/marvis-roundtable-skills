# 纯粹性判据手册（simplicity-criteria）

供 `role-jobs` 使用的判据手册。目的是让「更简单 / 更复杂」从感觉变成**可以逐项数、逐条争**的判断。
本手册不产出观点，只提供计数口径、模板与判别表。

## 1. 复杂度审计表：四类指标怎么数

**计数原则**：只数**最终使用者/最终结果承担的部分**，不数实现者自选的内部结构。
同一对象在不同指标里可能都要计一次，这不是重复计数，是不同维度的成本。

| 指标 | 数什么 | 怎么数（可操作口径） | 常见数错的地方 |
|------|--------|----------------------|----------------|
| 功能点数量 | 用户可见的能力 | 每一件用户能**主动发起**的事算 1；同一能力的不同入口合并算 1 | 把后台开关、内部配置算成功能点 |
| 状态数 | 用户需要理解的系统状态 | 用户需要知道「现在处于哪种情况」的不同情况数；含加载、空、失败、部分成功、只读、待审核等 | 只数正常态；把错误态当成例外不计 |
| 需要用户做的决策数 | 用户必须自己选的地方 | 从进入到完成目标，每一个「必须由人选择才能继续」的点算 1；有默认值且默认可用的算 0.5 | 把有合理默认的选项也算满 1 |
| 跨团队依赖数 | 需要外部配合才能推进的环节 | 每一个「对方排期不由本团队决定」的交接点算 1；同一团队多次交接合并算 1 | 把同一团队内分工算成跨团队 |

**输出格式建议**（写进 claim 的 `evidence`）：

```
复杂度审计：功能点 6 / 状态数 9（其中异常态 5）/ 用户决策 4（含默认 2）/ 跨团队依赖 3
与上一版对比：功能点 +1，状态数 +3，决策 +0，依赖 +1 → 本轮方向为更复杂
```

**注意**：指标只提供方向，不自动给出结论。某个指标变高并不等于方案更差——
第 4 节的判别表决定它属于哪一类复杂度。

## 2. 减法清单模板

减法清单必须是**可删对象的列表**，不是形容词列表。每条按下面的结构写：

```
- 删除对象：<具体的功能 / 步骤 / 状态 / 字段 / 角色 / 会议 / 审批层级 / 文档>
  当前由谁使用：<指名角色；写不出名字的写「无人可指名」>
  删除后谁承担代价：<具体代价与承担者；无代价写「未见代价」>
  恢复方式与恢复时间：<若需恢复，怎么加回来、大约多久>
  结论：删除 / 降级为可选 / 保留（保留须给第一理由）
```

**合格示例的形态**：
「删除对象：周报中的进度百分比字段。当前由谁使用：无人可指名（抽查 4 份周报，读该字段的人无法看出实际用法）。
删除后谁承担代价：向上汇报时缺少一个粗略进度信号，由直属主管承担。恢复方式：从任务系统重新聚合，约半天。」

**不合格的形态**（出现即重写）：
「优化审批流程」「简化页面信息层级」「提升整体体验」——没有删除对象，无法执行。

**标记规则**：删不掉的条目要在清单里写明**卡在哪里**（哪条约束、哪一方不同意），
不能含糊地留在「待讨论」里。

## 3. 终点倒推法

从**使用者可感知的结果**出发，反推最少步骤，再与现状对照。

**三步操作**：

1. 写终点：一句话描述使用者拿到什么、达成什么状态。终点不能是「流程走完」「节点通过」。
2. 反推步骤：从终点往前问「要在这一步成立，上一步最少必须发生什么」，直到起点。
   每一步标注「**谁需要它**」——必须能指到具体角色或具体结果。
3. 对照现状：把当前方案里的环节逐个往倒推链上贴，分三类：
   - **在链上**：倒推链要求它存在；
   - **不在链上但有人需要**：写清谁需要、为什么不在链上（通常是约束，见第 4 节）；
   - **不在链上且无人可指名**：候选删除项，进第 2 节模板。

**需求方判定口径**：

| 写法 | 判定 |
|------|------|
| 具体角色 / 具体岗位 / 具体下游结果 | 有效 |
| 「大家」「公司」「行业」「监管部门」（无具体条款） | 无效，需追问到能指名的层级 |
| 「以后可能用到」「万一要查」 | 无效，除非能给出具体事件类型与发生频率量级 |

**示例形态**：

```
终点：用户拿到退款到账确认。
反推：到账确认 ← 退款执行 ← 退款审批 ← 退款申请 ← 用户发起
现状对照：退款审批（谁需要：财务，因单笔限额约束）→ 不在链上但有人需要
          退款二级审批（谁需要：无人可指名）→ 候选删除项
```

## 4. 必要复杂度 vs 偶然复杂度判别表

对每一条被质疑的复杂度，问四个问题。**任一项落在右列，就先按必要复杂度对待**，
不当场删除，转而要求给出约束的具体来源。

| 判别问题 | 偶然复杂度（可减） | 必要复杂度（须先承认） |
|----------|--------------------|------------------------|
| 它对抗的失败是否不可逆？ | 失败可重来、代价可承受 | 数据丢失、资损、人身安全、不可撤回的对外承诺 |
| 它是否来自外部强制？ | 来自内部习惯、历史约定 | 法律条款、监管要求、合同义务、平台硬性限制 |
| 它是否是恢复/追责所需？ | 事后无人查看、无人追责 | 审计留痕、可回滚点、责任认定 |
| 它是否存在真实的少数使用者？ | 使用者不可指名或已不存在 | 能指名且仍在活跃使用（哪怕人数很少） |

**判别表的使用纪律**：

- 四问全落左列，才允许进入减法清单；
- 落右列时，**必须把约束的出处写出来**（具体条款 / 具体事件 / 具体使用者），
  写不出出处的「约束」按左列处理，但要在 claim 里标为待核实；
- 「必要」不是永久牌照：约束可能已失效，此时应记录为「约束存在但适用性待定」，
  由持有数据的一方确认，而不是由本角色单方面判定不存在。

## 5. 8 个抽象化工作场景（正反例）

每个场景给出**保留派理由**与**减法派回应**。这些是论点的骨架，不是结论；
真实议题中须替换为可指名的角色与事实。

**例 1 · 每周固定评审会**
- 保留派理由：让相关方同步信息，避免各自为政。
- 减法派回应：同步可以异步完成；要指名每周必须由人当面决定的**具体事项**。
  若无法指名，则降级为「有变更时召开」，并把每周会议记录中实际产生的决定数列出来。

**例 2 · 多级审批**
- 保留派理由：控制风险，防止越权。
- 减法派回应：先查每一级的**否决案例数**。否决数为零的层级，其功能与抄送相同，
  可降级为通知；保留唯一真正承担责任的签批层级。

**例 3 · 为兼容而保留的旧流程**
- 保留派理由：仍有旧版本用户/旧系统在用。
- 减法派回应：把兼容面拆成「有人正在用」与「担心有人还在用」两组，前者保留并给出下线条件，
  后者需要证据；同时要求写明**这个兼容层自身的维护代价由谁承担**。

**例 4 · 上线前必须填的三张表**
- 保留派理由：风险登记与合规留痕。
- 减法派回应：逐字段问「这个字段在事后被谁看过、看过几次」。零查看字段删；
  有查看的字段保留并注明查看场景。若来自条款要求，指出具体条款。

**例 5 · 为了统一而设的中台/公共层**
- 保留派理由：复用，避免重复建设。
- 减法派回应：统计实际接入方数量与接入耗时。接入方少且各自差异大的公共层，
  会把差异成本集中到所有接入方，属于把局部复杂变成全局复杂。

**例 6 · 用户注册前的实名/资质校验**
- 保留派理由：合规与风控要求。
- 减法派回应：这属于第 4 节右列，承认其为必要复杂度；
  可讨论的只是**时机**（前置还是首次使用前）与**表单字段数**，而不是是否保留校验本身。

**例 7 · 双人复核的发布流程**
- 保留派理由：防止误操作造成不可逆故障。
- 减法派回应：确认故障是否不可逆。不可逆则保留复核，但可把复核对象从「全部发布」
  收窄到「高风险变更」；可逆场景的复核可降级为事后告警。

**例 8 · 需求文档的固定十章模板**
- 保留派理由：保证信息完整，便于评审。
- 减法派回应：抽查历史文档中实际被引用的章节。长期空白的章节与「为了完整而完整」的章节删去，
  保留真正被下游（开发、测试、运营）引用的章节，并允许按需求类型裁剪。

**跨例共同判据**：保留派的理由若只落在「万一」「惯例」「统一」上，属于偶然复杂度的嫌疑；
若落在「不可逆」「外部强制」「能指名的使用者」上，按必要复杂度处理。

## 6. 警告：什么时候减法会造成风险

减法在本手册中**默认不是安全动作**。以下领域里，减法必须以「先证明可以」为前提，
而不是「先删掉，出问题再加回来」：

1. **安全**：权限校验、鉴权、输入校验、密钥轮换。
   这类环节平时看起来是零收益的纯成本，只有被绕过时才体现价值；
   删除后的问题往往不可逆。
2. **合规与法务**：审计留痕、披露义务、数据留存期限、可追溯的签批。
   判据是具体条款而非「感觉没必要」，删除须由法务/合规确认，不属于产品视角可单方裁定的范围。
3. **可恢复性**：备份、回滚点、幂等设计、灰度与终止开关。
   与「删除后多久能恢复」直接挂钩；恢复时间超过可接受窗口的，不得删。
4. **不可逆的对外承诺**：已对用户公布的价格、SLA、退款政策、数据导出承诺。
   减法的对象是内部步骤，不是对外承诺；承诺要变更须走独立决策路径，而非在本角色主张里顺手改掉。
5. **少数但依赖度高的使用者**：无障碍支持、低频但关键的操作路径（如紧急停用）。
   使用人数少不等于可删，要看**一旦需要时的替代方案是否存在**。
6. **人与关系的成本**：取消某个会议、某一层审批，同时会取消一个信息流动渠道与责任边界，
   这部分代价通常不写在流程图里，需要在 claim 的 `evidence` 中显式补上。

**遇到以上领域的标准动作**：
把该条从「候选删除项」改为「必要复杂度（约束：具体条款/具体风险）待确认」，
在 `claims` 中保留为 `value_judgment` 或 `case`（附来源），
并把「谁有权确认这条约束仍有效」写进 `uncertainty_points`。
承认必要复杂度不是对本角色的否定——把必要复杂度误当偶然复杂度删掉，才是。
