# 案例归纳操作手册（case-based reasoning）

本手册是 `role-pg` 的执行附件：把「从具体案例往上归纳」拆成可检查的步骤。它只处理**怎么用案例**，不处理议题本身的立场。

## 1. 案例记录模板

每个案例在写进 `evidence` 之前，先按下面五栏填一遍。填不满的栏必须写明「不适用」或「未知」，**不允许留空、不允许补全**。凡是补全出来的细节，都会在后续被当成事实使用，这是归纳法最大的污染源。

| 栏位 | 要写什么 | 常见错误 |
|------|----------|----------|
| 背景 | 谁、什么时候、在什么约束下（团队规模、资源、外部环境） | 用今天的环境描述当年的决策 |
| 动作 | 具体做了什么，可观察到的那一部分 | 写「他们很专注」这种评价而不是动作 |
| 结果 | 可观察的结果，含好的和坏的 | 只写成功结果，省略副作用 |
| 反事实 | 如果没做这个动作，最可能发生什么；判断依据是什么 | 默认「不做就一定失败」 |
| 可迁移边界 | 这个案例里哪些条件变了，结论就不再适用 | 把结论当普适规律直接搬到别的场景 |

**填写示范（抽象化场景）**：一个三四人的小团队，在预算有限、没有明确用户画像的阶段，先做内部自用的小工具并持续迭代，几个月后这个工具演化成对外产品。反事实栏应写：同期他们也尝试过直接做完整平台，但因为交付周期长、没有及时反馈而搁置；因此「先做小工具」在当时至少不是唯一选项。可迁移边界栏应写：这条经验依赖「外部没有强合规约束」「用户能直接接触到开发者」两个条件，条件变了就不适用。

**纪律**：反事实栏是最容易被跳过的一栏，也是最关键的一栏。没有反事实，案例只能说明「发生过什么」，不能说明「这个动作起了什么作用」。

## 2. 案例质量的五个判据

对每个候选案例逐一打勾，勾不满 3 条的案例不要用来做 `basis: case` 的论据，或者把 `confidence` 压到 40 以下。

1. **事实可核实**：是否至少有一份公开可查或可被当事人确认的记录？只有转述与印象的，算轶事不算案例。
2. **结果可归因**：结果能否在时间上、机制上回溯到那个动作？如果结果比动作晚了很久，或中间有大量并行变化，归因强度自动降级。
3. **有对照组**：同期是否有「没做这个动作」的可比对象？有对照的观察，比单向叙述强一档。
4. **有足够时间跨度**：结果是否已经稳定？刚开始变好的案例常常还没到见分晓的时候。
5. **不是幸存者**：这个案例是不是因为「成功」才被保存和讲述的？如果是，它就只能说明「成功者里有人这么做过」，不能说「这么做会成功」。

**用法**：五条全中 → 可支撑中等以上 `confidence`；中三条 → 只能是弱证据，必须显式写不确定性；中两条及以下 → 不要用来做论据，改写为 `intuition` 并降低 `confidence`。

## 3. 归纳强度分级表

| 级别 | 证据形态 | 能支撑什么 | 不能支撑什么 | 建议 confidence 区间 |
|------|----------|------------|--------------|----------------------|
| L0 · n=1 轶事 | 一个案例，无对照 | 「存在这种可能」 | 任何频率或因果断言 | ≤ 40 |
| L1 · 多案例一致 | 3 个以上独立案例方向一致，仍无对照 | 「这可能是常见模式」 | 「这么做就会导致这个结果」 | 45–60 |
| L2 · 有对照的对比 | 同期可比对象中，做与不做的结果有稳定差异 | 「在给定条件下，该动作与结果相关」 | 强因果，以及超出边界条件的推广 | 60–75 |
| L3 · 可重复实验 | 同一条件下重复得到同一结果 | 机制的因果解释，可外推到相似条件 | 外推到条件不同的场景 | 75–90 |

**升级路径**：L0 → L1 靠增加**独立**案例（同一来源的重复叙述不算增加样本）；L1 → L2 靠补充对照组；L2 → L3 靠可重复性。**跨级声明是常见越界**：从 L0 直接说成 L3 的口气，是本角色最需要避免的失误。

**注意**：创业、写作、组织管理类议题，绝大多数情况下拿不到 L3。此时正确的做法是**把证据标准写下来**（「本议题最高只能到 L2」），而不是含糊地说「多看看案例」。

## 4. 从案例写模式的句式模板

### 模板

- 标准式：**在 X 条件下，做 Y 会导致 Z。**
  - X = 边界条件（谁在做、资源与外部约束）
  - Y = 可观察的动作
  - Z = 可观察的结果，含时间尺度
- 收窄式（找到反例后用）：**在 X 条件下且 X' 也成立时，做 Y 会导致 Z；当 X' 不成立时，Y 与 Z 的关系不成立。**
- 失效声明（必写）：**当条件 W 出现时，本模式失效，因为**……

### 正例

- 「在用户能直接接触到开发者的早期阶段，先交付一个功能不完整的可用版本，会在数周内拿到可用于改进的真实反馈。」边界清楚、结果可观察。
- 「在合规要求严格且交付责任明确的场景下，先交付不完整版本会导致返工成本高于一次性设计。」同一个动作在不同 X 下结论相反，这才是模式该有的样子。

### 反例（禁止写成这样的句子）

- 「要尽早发布，快速迭代。」——没有 X，也没有 Z 的可观察标准。
- 「专注是创业成功的关键。」——不是条件句，是口号。
- 「做小工具更容易成功。」——把动作与结果的因果关系说得比证据强，缺边界条件与时间尺度。
- 「因为 A 公司做小工具成功了，所以我们也要做小工具。」——n=1 直接外推，且遗漏了 A 公司的其他条件。

### 自检问法

写完之后问三句：**反例在哪？**（找过没有）、**边界在哪？**（条件变了还成立吗）、**Z 怎么观察？**（多久、用什么指标）。三句有两句答不上来，这条模式就不能作为本轮的主要 claim。

## 5. 8 个抽象化工作场景

以下场景都是**抽象化的工作情形**，不含任何真实公司或人物的未公开事件。每个场景给出：案例事实、可提炼的模式、以及模式在什么条件下失效。

### 5.1 小团队先做小工具再做大平台

- **案例事实**：一个三四人团队，先交付一个只解决自身问题的小工具，边用边改；一年后在此基础上扩展成对外产品。同期另一条路线是直接立项做完整平台，因周期长、反馈少而被搁置。
- **提炼的模式**：在团队规模小、需求不确定、用户能直接反馈的条件下，先交付最小可用工具会导致更快拿到真实需求信息。
- **何时失效**：需求已被监管或合同明确写死；或小工具的技术选型无法承载后续规模，导致重建成本超过一开始就做对设计的成本。

### 5.2 早期用户来自熟人网络

- **案例事实**：产品最初的使用者集中在创始团队的职业关系网内，反馈快、容忍度高；当扩展到陌生人用户时，留存明显下降。
- **提炼的模式**：在缺乏渠道预算的早期阶段，从熟人网络获取前一批用户会导致反馈速度更快，但用户构成偏乐观。
- **何时失效**：产品面向的是与团队画像差异很大的群体；或熟人出于关系给出的使用行为不代表真实付费意愿。

### 5.3 主动缩减功能范围以换取交付

- **案例事实**：原计划的多模块方案被砍到一个核心流程后按时上线，上线后用户只高频使用其中一小部分功能。
- **提炼的模式**：在交付压力明确且用户尚未验证需求的条件下，砍掉非核心功能会导致按期交付，但会遗漏次要场景的用户。
- **何时失效**：被砍掉的功能恰是合规或安全前提；或用户选择该产品的理由正是那些被砍掉的次要场景。

### 5.4 把内部文档公开化带来外部用户

- **案例事实**：团队把内部使用说明整理后公开发布，随后有外部读者据此开始使用产品。
- **提炼的模式**：在产品需要解释成本较高的条件下，把内部材料整理成公开文档会导致外部获取成本下降。
- **何时失效**：文档内容涉及客户数据或未公开技术细节；或产品的问题是可信度而非理解成本，公开文档解决不了。

### 5.5 先做付费用户再考虑规模

- **案例事实**：一支小团队只服务少量愿意付费的客户，收入不高但持续为正；同期追求规模的同类项目在补贴结束后快速流失。
- **提炼的模式**：在单位获客成本高于用户生命周期价值的条件下，先服务少量付费客户会导致单位经济模型更早显现。
- **何时失效**：所在市场存在明显的网络效应，规模不足则产品价值本身无法成立。

### 5.6 写作中的「先说结论再展开」

- **案例事实**：同一批读者面对两个版本：先给结论再给论据的版本，和按推理顺序展开的版本；前者被完整读完的比例更高，但被质疑细节的比例也更高。
- **提炼的模式**：在读者注意力有限且需要快速判断的条件下，先给结论会导致更高读完率，但会放大对细节的争议。
- **何时失效**：读者是需要逐步验证的同行评审场景；或结论高度反直觉，直接抛出会触发防御性拒绝。

### 5.7 重构前先补测试

- **案例事实**：在缺乏测试的项目上做结构重构，短期内改动加快，随后因难以察觉的回归问题频繁返工；另一条并行路线是先补关键路径测试再重构。
- **提炼的模式**：在系统缺乏回归保护的条件下，先补关键路径测试再重构会导致前期变慢、后期返工显著减少。
- **何时失效**：代码即将废弃，测试投入无法收回；或关键路径本身尚在快速变化，为它写的测试很快失效。

### 5.8 通过减少会议频率提高交付量

- **案例事实**：某团队把每日同步改为每周一次、其余异步沟通，交付数量在数月内上升，但同时出现了跨模块协调问题暴露较晚的情况。
- **提炼的模式**：在任务彼此独立、接口稳定的条件下，降低同步频率会导致可用工时增加。
- **何时失效**：任务高度耦合、接口频繁变化；此时延迟暴露的协调问题会把节省的时间加倍还回去。

**统一提醒**：以上八个场景的模式都停在 L1 到 L2 之间，**没有一个够得上 L3**。引用它们时必须带上边界条件，不能把「在某种条件下曾经这样」说成「就应该这样」。

## 6. 自我警示：案例集本身就是被筛选过的

这一节是本手册最重要的部分，因为它约束的是**整个方法的地基**。

1. **幸存者偏差是结构性的，不是态度问题**。能被记住、被讲述、被写进公开材料的案例，绝大多数是活下来或被认真复盘过的那些。失败者的过程通常没有人记录，也就不会进入你手里的样本。你看到的不是「做过这个动作的总体」，而是「做过这个动作且留下来被讲述的子集」。
2. **禁止用「我见过好几个都这样」冒充统计证据**。这句话只证明你有印象，不证明你有样本。要把它变成证据，必须逐个给出：谁、什么时候、做了什么、结果如何，并且说明这些案例是从哪个范围里挑出来的——特别是**没被挑进来的那部分长什么样**。
3. **同一来源的多次叙述不算多个样本**。同一个故事被不同文章转述，样本量仍然是 1。判断独立性看事实来源，不看表述次数。
4. **讲故事的人有立场**。回忆录、宣传材料、成功者访谈都会系统性美化决策过程与因果关系。看到单向叙述时，默认它省略了至少一个不利因素。
5. **缺失的样本比存在的样本更重要**。在你归纳出模式之后，必须问一句：**符合这个模式却失败的情况，我为什么没有看到？** 如果答案是「没人记录」，那么这个模式的证据强度就要往下降一级。
6. **降低表达强度而不是放弃归纳**。正确做法不是「什么都不说」，而是把强度诚实标出来：能到 L1 就说 L1，用「可能是常见模式」而不是「规律就是」。
7. **优先记录失败案例**。本方法唯一的自我纠正机制，是主动积累反例与失败记录。任何一次讨论结束后，若有反例或失败案例被提出，应该被保留下来，而不是当作噪音丢弃。
