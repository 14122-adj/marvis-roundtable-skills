# 工具调用协议

`ultimate-roundtable` V3.0 的核心纪律：**数据诉求必须闭环**。
本文件规定 `[Tool Call]`、真实/模拟边界、闭环校验、以及 `[打断并验真]` 的落地方式。

## 目录

1. 两种工具调用
2. 真实 vs 模拟的边界

## 1. 两种工具调用

### Search

```
[Tool Call: Search] 关键词：季度评审 上下文切换成本 案例
```

- 用途：找**外部事实**——公开数据、案例、标准、政策条文；
- 必须写清关键词（不是"查一下相关资料"）；
- 拿到结果后必须紧接着写 `基于此数据，我的观点是…`。

### Code

```
[Tool Call: Code] 目的：验证包装成本占比达到多少会让结论反转
```python
base = 100
packaging = 0.12
print("占比", packaging, "→", "反转" if packaging > 0.15 else "不变")
```
```

- 用途：**验证一个可计算的判断**——量级估算、阈值、敏感性；
- 代码要短（10 行内）、可复现、不依赖外部文件；
- 运行结果必须原样贴出来，不能只写"跑了一下，大概对"。

## 2. 真实 vs 模拟的边界

| 情形 | 标注方式 |
|---|---|
| 宿主真的执行了搜索/代码 | `{"source": "tool", "tool": "web_search", "result": "…"}` |
| 宿主没有工具能力，用推理构造 | `{"source": "text", "simulated": true, "result": "…"}` |

**三条红线**：

1. `source: "tool"` 与 `simulated: true` **不能同时出现**（自相矛盾）；
2. 两者都不标 → 判定为"把模拟数据伪装成真实数据"，**拒绝进入下一阶段**；
3. 报告头部会打印「阶段一 真实 N / 模拟 M；沙盘 真实 X / 模拟 Y」——
   这个数字不能改，它是读者判断证据成色的唯一依据。

**模拟数据的写法纪律**：结果前面加 `（模拟）` 或 `simulated: true`，
并在心里清楚：**模拟数据只能用来演示机制，不能用来支撑真实决策。**

## 3. 闭环三要素

一条角色发言要算"闭环"，必须三样齐全（脚本逐条检查，缺一即整体拒绝）：

| 要素 | 正则 | 说明 |
|---|---|---|
| 数据诉求 | `\[数据诉求[:：]\s*(.+?)\]` | 我依赖什么数据 |
| 工具调用 | `\[Tool Call[:：]\s*(Search|Code)\]` | 我怎么拿到的 |
| 明确表态 | `基于(此|该|这)(数据|结果|查证)` | 拿到之后我怎么改判断 |

**不合格样例**：

```
❌ 我需要更多数据才能判断。                    （有诉求，无调用，无表态）
❌ [数据诉求: 需要留存曲线] 我觉得留存会下降。  （有诉求，无调用）
❌ [Tool Call: Search] 关键词：留存。          （有调用，无诉求，无表态）
❌ 查到了，留存确实下降。                       （无诉求，无调用，无标准表态句）
```

**合格样例**：

```
✅ 我的结论依赖留存基线。[数据诉求: 需要过去 12 个月的月度留存曲线]
   [Tool Call: Search] 关键词：SaaS 月度留存 基准值。
   基于此数据，我的观点是：留存下降 8% 属于正常波动，不构成否决理由。
```

## 4. 验真（`[打断并验真]`）

V3 新增的辩论动作。与普通 `[打断]` 的区别：

| | `[打断]` | `[打断并验真]` |
|---|---|---|
| 做什么 | 指出对方假设未验证 | 指出 + **当场去查** |
| 要求 | 给出具体质问 | 质问 + `[Tool Call]` 或 `verify_result` |
| 缺结果的后果 | 记为无效交锋 | **阶段二直接拒绝** |

`verify_result` 的三种 `verdict`：

| verdict | 含义 | 后续要求 |
|---|---|---|
| `supported` | 查证支持对方主张 | 打断方必须承认，或说明为什么证据不够 |
| `refuted` | 查证推翻对方主张 | 被质疑方必须修正或给出反驳证据 |
| `inconclusive` | 查不到决定性证据 | 该前提应登记为 `Need Info`，不得当成已解决 |

**只打断不查证是最糟的行为**：它会让讨论看起来在推进，实际上谁也没拿到新信息。

## 5. 沙盘阶段的工具要求

阶段三的 `sandbox.tool_calls` 至少 1 条，且必须：

- `purpose` 写清要验证哪条**假设**（不是"看看情况"）；
- `Code` 类型必须有 `code` 字段，且代码可独立运行；
- `result` 必须有内容（空结果等于没验证）；
- 同样遵守真实/模拟标注。

**为什么沙盘必须要工具**：V2 的沙盘是"模拟数据倒逼修改"，
V3 要求至少有一个数字是**算出来的**而不是编出来的——
这是"内部推演"和"现实验证"的分界线。

## 6. 常见错误与判定结果

| 错误 | 脚本判定 | 退出码 |
|---|---|---|
| 有 `[数据诉求]` 无 `[Tool Call]` | 阶段一失败 | 3 |
| 有 `[Tool Call]` 无表态句 | 阶段一失败 | 3 |
| `source: tool` + `simulated: true` | 阶段一失败 | 3 |
| 两者都不标 | 阶段一失败（伪装数据） | 3 |
| `[打断并验真]` 无结果 | 阶段二失败 | 3 |
| 沙盘无 `tool_calls` | 阶段三失败 | 3 |
| `Code` 调用缺 `code` | 阶段三失败 | 3 |
| 攻击不足 / 全是空洞发言 | 阶段二 `no_spark` | **4** |

## 7. 在无工具能力的环境里怎么办

有些宿主（纯文本对话）没有搜索或代码执行能力。此时：

1. **仍然要写 `[Tool Call]`**，但 `tool_result` 必须标 `simulated: true`；
2. 报告头部的统计会如实显示"真实 0 条 / 模拟 6 条"——**这不是失败，是诚实**；
3. 结论中所有依赖模拟数据的地方，必须进入 `Need Info` 栏，
   并在文字里写清"这个数字是构造的，需要实测替换"。

> 宁可交一份写着"全部为模拟数据"的报告，
> 也不要交一份看不出哪条是真的报告。
