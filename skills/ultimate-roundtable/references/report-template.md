## 1. 冻结的报告模板

`ultimate_orchestrator.py report` 输出的就是这个结构，**顺序与标题不可改动**：

```markdown
### 📊 终极圆桌决策报告

> 议题：……　会话：`ur-20261101-012900`　数据来源：真实工具调用 3 条 / 模拟数据 3 条

#### 1. 核心共识与分歧底牌
- **共识**：xxx
- **核心分歧（未被完全解决）**：xxx

#### 2. 击穿的隐性假设（元认知发现）
- 全程共同的隐性假设：**xxx**
- 我们一开始默认了 xxx，但沙盘推演证明这是错的。
- 我们忽略了 xxx 维度的成本。

#### 3. 行动指令 (Action Items)
- ✅ **Do（立刻执行）**：xxx
- ❌ **Don't（绝对禁区）**：xxx
- 🔍 **Need Info（需要补充调研）**：xxx

#### 4. 沙盘推演存活率评估
- 当前方案的预估存活率：62%（满分100%）
- 最致命的潜在风险点：xxx

#### 5. 长期记忆写入
- `[MEMORY_UPDATE]`：xxx

---

**过程留痕（不属于报告正文）**

- 阶段一数据诉求 6 条：
  - [musk] 需要 2024 年 Q3 的竞品营收数据
- 红蓝分组：蓝军 [...] ｜ 红军 [...]
- 对抗火花：攻击 3 / 防御 2 / 靶点 2 / 空洞发言 0 → **sparked**
- 动态召唤：法务专家
```

**头部那一行数据来源统计不能省**：它让读者在 3 秒内判断这份报告的证据成色。
真实调用 0 条、模拟 6 条的报告，和真实调用 6 条的报告，可信度完全不同。

## 2. 合格 / 不合格对照

| 板块 | 合格 | 不合格 |
|---|---|---|
| 共识 | "现行分配规则本身在制造额外成本（musk/pg 均支持，强度 majority）" | "大家一致认为应该优化流程" |
| 核心分歧 | "成功标准是否必须等于获奖——**价值分歧**，逻辑无法消解，只能各自说明条件" | "还有一些细节需要进一步讨论" |
| 隐性假设 | "我们一开始默认了『成功=获奖数』，沙盘显示第 3 个月有效产出下降 8%" | "我们可能忽略了一些重要因素" |
| Do | "先在一级评审上做三个月对照试点，指标为包装投入占比与有效产出" | "加强沟通、持续优化" |
| Don't | "不要一次性全量切换评审口径（试点未验证前）" | "不要犯错" |
| Need Info | "过去两年因评审拦截造成的损失记录（用于验证评审必要性）" | "需要更多数据" |
| 存活率 | "62%（high 分档不足，因 evidence_coverage 只有 33%）" | "大概七八成吧" |
| 最致命风险 | "长期项目停摆（severity 0.9 × probability 0.4）" | "存在一定风险" |
| 长期记忆 | 见第 4 节 | 把会议纪要原样贴进来 |

**判定口径**：凡是没有主语、没有判据、没有数字的句子，一律视为不合格——
这正是 spec 里"禁止使用『我觉得挺好的』『大家都很努力』"的可执行版本。

## 3. 存活率手算示例

已知沙盘数据：

```json
{
  "risks": [
    {"name": "包装成本失控", "severity": 0.8, "probability": 0.6},
    {"name": "长期项目停摆", "severity": 0.9, "probability": 0.4},
    {"name": "评审反弹",     "severity": 0.3, "probability": 0.5}
  ],
  "key_assumptions": [
    {"text": "成功标准=获奖",     "evidence": ""},
    {"text": "包装成本可控",       "evidence": "示例量级估算"},
    {"text": "团队会配合新口径",   "evidence": ""}
  ],
  "attacks": [{"text": "包装成本", "defended": true},
              {"text": "长期项目", "defended": false}],
  "action_plan": {"do": ["试点"], "dont": ["全量切换"], "need_info": ["损失记录"]}
}
```

手算：

```
risk 各项 = 0.8×0.6 = 0.48 ；0.9×0.4 = 0.36 ；0.3×0.5 = 0.15
平均 = (0.48+0.36+0.15)/3 = 0.33
risk_residual     = 100 × (1 - 0.33) = 67.0

evidence_coverage = 1/3 → 33.3
defense_quality   = 1/2 → 50.0
plan_integrity    = 3/3 → 100.0

survival = 0.40×67.0 + 0.25×33.3 + 0.20×50.0 + 0.15×100.0
         = 26.8 + 8.3 + 10.0 + 15.0
         = 60.1  → 60%
```

**为什么要能手算**：任何一个分项都能被单独挑战——
"你凭什么叫 0.9 的 severity？"就是一场有价值的讨论。
而"存活率 60%"如果算不出来，就只是一个装饰。

**band 判定**：`60%` 落在 `40–69`，属 `medium`：
可以交付但要附条件；若是 `<40` 则**不得直接交付**，必须先补 Need Info 或改设计。

## 4. 长期记忆（≤200 字）写法

**它是什么**：一条**下次能直接复用的判断**，不是这次发生了什么。

**结构建议**（不强制，但包含这些要素的更耐用）：
`触发条件` + `机制` + `可操作动作`

**合格样例（98 字）**：
> 分配机制一旦以单一可包装指标为度量，就会催生为指标服务的成本；
> 先定义成功标准再谈资源分配，是这类议题唯一的前置动作。

**不合格样例**：
- ❌ "本次讨论很成功，大家提出了很多有价值的观点。" —— 无信息量；
- ❌ 把六个人的发言摘要贴一遍 —— 超过 200 字，且不可复用；
- ❌ "要注意风险。" —— 无触发条件、无机制、无动作。

**字数怎么算**：按中文字符计（`len(memory)`），超过 200 直接拒绝写入。
不是建议，是硬门槛——超长记忆在下一次被读取时会被截断，等于白写。

## 5. 阶段三 `sandbox.json` 完整字段

```json
{
  "sandbox": {
    "plan": "方案 A：按能力覆盖分配 + 保留一级评审",
    "runners": ["karpathy", "musk"],
    "timeline": [
      {"month": 1, "event": "评审表上线，团队开始包装材料", "metric": "包装投入占比 12%"},
      {"month": 3, "event": "包装成本吃掉预算",           "metric": "有效产出下降 8%"},
      {"month": 6, "event": "长期项目被挤占",             "error": "两个跨年度项目停摆"}
    ],
    "risks": [{"name": "包装成本失控", "severity": 0.8, "probability": 0.6}],
    "key_assumptions": [{"text": "成功标准=获奖", "evidence": ""}],
    "attacks": [{"text": "包装成本", "defended": true}],
    "action_plan": {
      "do": ["先在小范围试点新口径"],
      "dont": ["不要一次性全量切换"],
      "need_info": ["包装成本占真实比例"]
    },
    "consensus": "现行分配规则本身在制造额外成本",
    "core_divergence": "成功标准是否必须等于获奖（价值分歧，未解决）"
  },
  "summons": [
    {"role": "法务专家",
     "reason": "评审口径变更涉及评奖规则与合规",
     "statement": "改口径需同步修改评奖细则，否则评奖结果可被申诉"}
  ]
}
```

**校验规则**（脚本强制执行）：

| 字段 | 要求 | 违反后果 |
|---|---|---|
| `plan` | 必填 | 拒绝（退出码 3） |
| `timeline` | ≥3 个节点，每个有 `month` + `event` + (`metric` 或 `error`) | 拒绝 |
| `runners` | 必须包含 `karpathy` 与 `musk` | 拒绝 |
| `summons[].role/reason/statement` | 三者齐全 | 拒绝 |
| `action_plan` 三栏 | 出报告时必须都非空 | 拒绝出报告 |

`severity` 与 `probability` 取 0–1 的小数。写不出精确值时给保守估计并说明依据，
**不要留空**——留空等于放弃风险评估。

## 6. 阶段四 `meta.json` 完整字段

```json
{
  "meta": {
    "shared_hidden_assumption": "成功必须用获奖来度量",
    "assumption_broken": ["成功标准等于获奖数", "包装成本可以忽略"],
    "ignored_dimension": "组织信任与长期项目机会成本",
    "consensus": "现行规则在制造额外成本",
    "core_divergence": "成功标准是否必须等于获奖（价值分歧，未解决）",
    "memory": "分配机制一旦以单一可包装指标为度量，就会催生为指标服务的成本；先定义成功标准再谈资源分配。"
  }
}
```

| 字段 | 含义 | 校验 |
|---|---|---|
| `shared_hidden_assumption` | **所有人**始终没跳出的前提（不是某个人的疏漏） | 必填 |
| `assumption_broken` | 被沙盘证伪的前提，≥1 条 | 必填非空 |
| `ignored_dimension` | 被忽略的成本维度 | 必填 |
| `consensus` / `core_divergence` | 报告第 1 节的两句话 | 必填 |
| `memory` | 长期记忆，≤200 字 | 超长拒绝 |

**区分两个容易混的字段**：
- `shared_hidden_assumption` 是**全场共同**的（所有人默认）；
- `assumption_broken` 是**具体哪条**被证伪了（可以是某个人提出的，也可以是被沙盘打掉的）。
  混为一谈会让"击穿隐性假设"变成一句空话。

## 7. 常见坏报告清单

1. **按轮次罗列发言**——报告是决策文档，不是会议记录；
2. **共识写成"大家一致认为"**——没有支持者、没有强度、无法追溯；
3. **分歧写成"还需进一步讨论"**——没说明它是事实分歧（可补数据）还是价值分歧（不可调和）；
4. **行动清单写"加强""优化""提升"**——没有主语、没有判据、没有完成标准；
5. **存活率没有分项**——读者无法判断它是怎么来的，也就无法反驳；
6. **风险只写"存在一定风险"**——没有 severity / probability，等于没做评估；
7. **长期记忆超 200 字**——下次读取会被截断，等于没写；
8. **把模拟数据写成真实数据**——最严重的错误，会让整份报告失去可信度；
9. **召唤角色凑数**——没有跨领域盲区却硬塞一个专家，稀释可信度；
10. **报告里出现"已达成共识""已验证"**——脚本会直接报错退出，
    因为这些词在证据不足时是最容易被用来和稀泥的措辞。
