# 观点迭代与立场演化

真实人会在辩论中被说服。固执到底的角色只是复读机，"为了共识"悄悄投降的角色则让讨论变成假共识。
本技能管住两头：**给修正开门，但不给从众开门**。

## 修正的三类触发（至少满足一条，且必须能被引用）

1. **新事实**：收到了此前未考虑过的证据（新 claim 的 id，或元认知登记的信息缺口 `G`）；
2. **无法反驳的论证**：对方提出了本角色思维协议无法处理的论证（对方 claim id）；
3. **隐性假设被点破**：元认知标记了某条前提（`H`），角色认可它确实值得质疑；
4. **自己的论据类型本身失效**：例如发现自己用的是类比（`basis: analogy`），而类比在该问题上已失效。

`trigger` 字段必须写出**是哪一个 id 触发的**。写不出 id，就不是有效修正。

## 三级修正幅度

| 级别 | 含义 | 判据 |
|---|---|---|
| `micro` | 保留核心立场，调整论据或边界条件 | `to` 与 `from` 的核心结论相同，只是加了限定条件 |
| `local` | 在某个子问题上改变立场 | 明确指出是哪个子问题，核心立场是否受影响 |
| `foundational` | 承认初始前提有问题（罕见） | 必须写出**原来的前提错在哪**；只写"为了达成共识"一律降级为 `local` |

`foundational` 稀缺是正常的。一场讨论里真正发生 0–1 次底层修正才是健康的；每次都底层修正说明角色没有立场，全是墙头草。

## 记录模板

```yaml
revision:
  trigger: "被 M1-1 的推演说服，且元认知提出 H1（竞赛必须拿奖才算成功）"
  level: local
  from: "资源应按历史规模分配"
  to: "资源应按边际收益分配，但需先定义收益口径"
  reason: "历史规模是路径依赖的结果，不是成功原因；但边际收益在当前缺少统一口径"
  remaining_doubt: "收益口径由谁定义，本身就是价值问题"
```

五个字段缺一不可。`remaining_doubt` 尤其重要——**它让修正不再是投降，而是带条件的推进**，
也是元认知层下一轮可以直接拿来用的新素材。

## 有效性判定与反从众机制

```bash
python scripts/revision_tracker.py record --state S --file pg-round2.json --write
python scripts/revision_tracker.py baseline --state S --role pg
python scripts/revision_tracker.py list --state S --role pg
```

判定规则：

| 判定 | 条件 | 结果 |
|---|---|---|
| **有效修正** | `trigger` 引用了存在的 claim id / `H`/`D`/`G`/`F`/`C` 编号 | 记录有效，并**改写该角色下一轮的立场基线** |
| **从众漂移** | `trigger` 没有任何引用，或理由只有"大家认为""为了推进讨论""保持一致" | `valid: false`；**基线不变**，`compliance_drift_count + 1` |
| **反复横跳** | 新立场与此前被放弃的立场高度相似，或累计修正 ≥3 次 | 标记 `unstable`，提示元认知介入核查 |
| **降级** | `foundational` 但没说明原前提错在哪 | 自动降级为 `local` 并给出告警 |
| **引用悬空** | 引用了不存在的 id | 记警告（可能是笔误或尚未登记），仍按引用处理 |

**基线不变**是整个机制的枢纽：角色可以说"我被说服了"，但如果拿不出新理由，
系统不会让这句话改变讨论状态。这样"共识"必须由证据推动，而不是由礼貌推动。

若确实是**用户在讨论中途提供了外部新事实**，用 `--allow-uncited` 放行，并在 `trigger` 里写清来源。

## 与编排层的接口

- 每轮开始前，编排层读 `baseline`：`source: revision R2(round 2)` 表示本轮起点已是被修正后的立场；
- 历史**不删除**：`from` 永远留在记录里，最终报告可以展示完整的立场演化路径；
- 交接给决策景观时，`remaining_doubt` 是"需要进一步信息"类建议的重要来源；
- 若某角色 `compliance_drift_count ≥ 2`，元认知层应在下一轮点名（"你连续两次在没有新证据的情况下改口，说明什么？"）。

## 修正发生时，角色要怎么说话

修正不是悄悄换一句话。正确做法：

1. 先**明确承认**："我第 1 轮的 M1-1 依赖一个我没论证的前提：X"；
2. 再说明**触发**（引用 id）；
3. 再给出**新立场与原立场的差异**（哪些结论变了，哪些没变）；
4. 最后写 **remaining_doubt**——修正后仍不确定的地方，避免新立场变成新的教条。

反例（不合格）："综合大家的意见，我同意多数人的看法。"——没有触发、没有差异、没有余疑，等于弃权。

## 反模式

1. ❌ 把修正当成绩效指标。修正次数多不等于讨论质量高；底层修正 0 次也完全可能是对的。
2. ❌ 无引用修正（从众漂移）被写成有效修正。
3. ❌ 修正后删除或改写历史记录（`from` 必须保留）。
4. ❌ 用 `foundational` 级修正包装一句简单的措辞调整。
5. ❌ 把修正当作"结束争论"的手段——修正只改立场，不改已经登记的质疑状态，未回应的质疑仍是 open。
6. ❌ 让六个角色在同一轮全部发生立场迁移。若出现这种模式，先查是不是注入的 `must_respond` 措辞带有引导性。
