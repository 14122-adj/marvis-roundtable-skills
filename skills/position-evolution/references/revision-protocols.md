`position-evolution` 的操作手册。用于判断一次修正该怎么记、记完之后基线怎么变。

## 1. 五类典型修正场景

### 场景 A · 事实驱动（`local`，最常见）
对方给出你此前没有的数据或案例。
```yaml
revision:
  trigger: "K2-1 给出的模块拆分显示我原来假设的耦合度不成立"
  level: local
  from: "两部分必须一起改，所以只能整体重构"
  to: "接口清晰时两部分可分别重构，但需要先补一层接口定义"
  reason: "耦合来自缺少接口约定，不是逻辑上的必然"
  remaining_doubt: "接口定义的成本是否真的低于一次性重构"
```
要点：新的边界条件是**证据给的**，不是自己让的。

### 场景 B · 论证驱动（`micro`）
对方没有新数据，但指出你的推理链里有一环是类比。
```yaml
revision:
  trigger: "G1-2 指出我的论证依赖与航空业的类比，而该类比在监管环境上失效"
  level: micro
  from: "按航空业经验，预算是主导瓶颈"
  to: "航空业经验只在监管强度相近时成立；本场景瓶颈可能是人才而非预算"
  reason: "类比失效点被指出，原结论的适用范围需要收窄"
  remaining_doubt: "本场景瓶颈到底是什么，仍缺数据"
```
要点：核心立场不一定变，但**适用范围被收窄**——这也是修正，值得记录。

### 场景 C · 前提被点破（`local` 或 `foundational`）
元认知层标出 `H`，你承认它确实值得质疑。
```yaml
revision:
  trigger: "H1（竞赛必须拿奖才算成功）被提出后，我承认我的资源分配结论依赖它"
  level: local
  from: "资源应该集中在最可能获奖的项目上"
  to: "资源分配取决于成功标准：若标准是能力覆盖而非获奖，分配逻辑完全不同"
  reason: "原结论只在'必须拿奖'这一目标前提下成立，而该前提本身未被论证"
  remaining_doubt: "成功标准由谁定义，这是价值问题不是事实问题"
```
要点：明确指出"我的哪条结论依赖该前提"，而不是泛泛承认。

### 场景 D · 误读修正（`micro`）
你发现自己误解了对方，或对方误解了你。
```yaml
revision:
  trigger: "重读 P1-2 后发现自己把'案例驱动'理解成了'不要数据'"
  level: micro
  from: "pg 主张只靠案例、不要量化"
  to: "pg 主张先有案例再有量化，看重点不同而非对立"
  reason: "原表述误解了对方主张，属于术语理解偏差"
  remaining_doubt: "无（但本方前一轮的质疑 C3 应标记为基于误读，需要撤回）"
```
要点：误读修正往往伴随**质疑撤回**，两件事要一起做。

### 场景 E · 用户介入（`local`，允许 `--allow-uncited`）
用户在讨论中途提供了外部事实。
```yaml
revision:
  trigger: "用户于本轮提供的实测数据（见 G3 补充）"
  level: local
  from: "三年总成本自建更低"
  to: "三年总成本自建更高，除非人力成本按当前口径的 60% 估算"
  reason: "外部实测数据直接推翻原估算的关键参数"
  remaining_doubt: "该数据是否覆盖了后续三年的规模变化"
```
优先做法：先把外部事实登记为 `G` 的补充或一条 `empirical` claim，再让 `trigger` 引用它；
只有来不及登记时才用 `--allow-uncited`，并在 `trigger` 里写清来源。

## 2. 有效与无效对照

| 表述 | 判定 | 原因 |
|---|---|---|
| "被 M2-1 的良率数据显示说服，调整结论范围" | ✅ 有效 | 引用了新证据 id |
| "H1 被提出后，我承认结论依赖它" | ✅ 有效 | 引用了元认知条目 |
| "综合大家意见，我同意多数看法" | ❌ 漂移 | 无引用、无理由 |
| "为了推进讨论，我放弃原立场" | ❌ 漂移 | 理由是从众 |
| "我觉得大家说得都有道理" | ❌ 漂移 | 无引用、无差异说明 |
| "对方的批评很有力" | ❌ 不完整 | 未说明哪条质疑、哪条结论变了 |
| "我修正一下措辞，结论不变" | ⚠️ 不算修正 | 措辞变化不需要 revision，直接改写即可 |

判断口径：**修正必须能回答"哪条结论变了"**。答不出就是措辞调整或从众。

## 3. 漂移识别细则

命中任一即判为 `compliance_drift`（基线不变）：

1. `trigger` 里没有任何 claim id 或 `H/D/G/F/C` 编号；
2. 理由中出现：为了达成共识 / 为推进讨论 / 大多数人 / 大家都 / 保持一致 / 顺应主流 / 少数服从多数；
3. `to` 与当前多数立场高度相似，而 `from` 是少数派立场，且没有新证据（相似度可用状态文件里的论断文本比对）；
4. 同一轮里超过 3 个角色同时发生立场迁移——**系统性漂移**，元认知层必须介入核查注入措辞是否有引导性。

处置：

- `positions[role].compliance_drift_count += 1`，基线**不变**；
- 元认知层下一轮点名："你在没有新证据的情况下改口，是哪些话语让你改的？"
- 连续 2 次漂移 → 在最终报告里标注该角色的立场"不稳定"，其置信度不应被计为有效支持。

## 4. 横跳识别细则

标记 `unstable` 的三种情况：

1. 新立场与此前被放弃的立场（某条 revision 的 `from`）相似度 ≥0.7，且原立场与那条 revision 的 `to` 也相似（即原路返回）；
2. 同一角色累计有效修正 ≥3 次；
3. 同一议题上 `from`/`to` 来回颠倒。

处置：`unstable` 不阻止修正，但要**在最终报告里展示完整演化路径**，并让元认知层问一句
"这两次改口的依据分别是什么？"——多数情况下会发现其中一次是漂移。

## 5. `foundational` 的判定门槛

必须同时满足：

1. 明确指出**原来的哪个前提**错了（写不出 → 自动降级为 `local`）；
2. 说明该前提错在哪：是事实错误、是适用范围错误，还是它本身是个价值选择；
3. 说明哪些结论随之改变（至少一条）；
4. `remaining_doubt` 非空——底层修正之后仍然有不确定的地方，说明这不是"彻底想通了"的表演。

合格样例："我的初始前提是'成本由技术决定'，这是错的：成本主要由组织激励结构决定（工具会做，
但没人有动力做）。因此结论从'投入研发即可降本'改为'先改考核口径，再谈研发投入'。"

不合格样例："我意识到我的根本假设有问题，需要重新思考。"——哪个假设？错在哪？结论怎么变？全无。

## 6. 撤回规程

修正不是唯一的历史动作，**撤回**同样要记录：

| 动作 | 何时用 | 记录方式 |
|---|---|---|
| `revision` | 自己的立场变了 | `revisions[]` 一条 `R` 记录 |
| 质疑撤回 | 发现自己上一轮的质疑基于误读 | `open_challenges[].status = "dropped"`，并在理由里写"基于误读（见 R2）" |
| 论断撤回 | 承认某条 claim 不成立 | 在该 claim 上加 `"retracted": true, "retracted_by": "R2"`（不要删除） |

撤回要显式说明**撤回的依据**；含混的撤回（"算了当我没说"）不改变状态。

## 7. 修正后的发言模板

修正发生时，该角色的本轮发言按此顺序组织：

```
1) 承认：我在第 1 轮的 M1-1 依赖一个未论证的前提 X。
2) 触发：这条前提是被 __（M2-1 / H1 / G3）点破的。
3) 差异：变了的是 __，没变的是 __。
4) 新立场：……（这就是本轮的 position 字段）
5) 余疑：remaining_doubt——新立场里我仍然不确定的地方。
6) 回应：本轮仍需回应的注入条目（must_respond）。
```

第 3 步最容易被省略，但它是**区分"真修正"与"假投降"的唯一证据**。
第 5 步则保证修正后的立场不会立刻变成新的教条。
