# 平民视角检查手册（plain-user-checklist）

供 `role-civilian` 使用。本手册不产出观点，只提供**可逐项过、可被质疑、可复算**的检查动作：把"这东西我能不能用"从感觉变成可以写进 claim 的记录。

## 1. 首次接触的五个观察点

顺序不能调换。**先看，再想，最后才动手**——一旦提前看了说明文档，观察就失效了，因为真实使用者往往没有那份文档。

| 顺序 | 观察点 | 记什么 | 合格记录的样子 | 不合格的样子 |
|---|---|---|---|---|
| 1 | **我要做什么** | 带着一个具体任务进来，而不是"看看这系统有什么功能" | "我要把上周的报销单交上去" | "了解一下产品定位" |
| 2 | **我看到什么** | 第一屏上实际出现的元素：标题、按钮文字、输入框标签、空白区 | "屏幕上有一个'新建'按钮和一句'请先选择组织'" | "界面比较简洁" |
| 3 | **我需要猜什么** | 每一处必须靠猜才能继续的地方 | "我不知道'组织'指的是哪个，也没看到可选列表" | "可能有点不直观" |
| 4 | **我担心什么** | 动手前的顾虑：会不会扣钱、会不会发错人、能不能撤回 | "我担心点下去就提交了，没有确认" | "有点没底" |
| 5 | **我会点哪里** | 我实际的第一动作，以及它是否通向我第 1 点写的任务 | "我会点'新建'，但它弹的是审批流，不是报销单" | "随便试试" |

**使用纪律**：

- 五个观察点必须**都写**，缺任何一个都不算完成首次接触测试；空白比编造好，写"这一屏没有让我产生担心"也可以。
- 第 3 点的每一条都必须指到具体位置（哪一屏、哪个字段、哪句话）。指不到位置的"需要猜"通常是事后编出来的。
- 第 5 点与实际结果不一致，本身就是最有价值的发现：**我以为的入口不是它设计的入口**，这句话可以直接写进 claim 的 `text`。

## 2. 动作计数表模板

数字是对抗"太繁琐"这种指控的唯一武器。没有口径的数字同样无效，所以每张表必须先把口径写在表头上。

**口径先声明（三选一，写在表上方）**：

- 只数必填项 / 必填 + 有默认值的可选项 / 全部可见项；
- 键盘操作与鼠标点击分别计数，还是合并为"动作"；
- 页面跳转按"换屏"算一次，弹窗与抽屉是否算换屏。

**表模板**：

| 任务 | 点击数 | 填写字段数 | 跳转页面数 | 等待/求助次数 | 是否成功 | 最刺眼的一处 |
|---|---|---|---|---|---|---|
| 任务 A（一句话写清，含输入物） | | | | | 是 / 否 / 部分 | |
| 任务 B | | | | | | |
| 任务 C（选一条出事时才会走的路径） | | | | | | |

**填写规则**：

1. 每行必须是一个**完整任务**，不能是"设置一下偏好"这种半截动作。
2. "是否成功"必须给三态之一，**不允许空着**。部分成功要写清卡在哪一步。
3. "等待/求助次数"指中途需要离开当前界面去找信息、找人、或者等别人的次数——这一列常常是真正让人放弃的地方。
4. "最刺眼的一处"每行只能写一处，且必须是前面几列里能对应的那一处；写不出对应关系，说明这行是凭印象填的。
5. 三行里**至少一行**要是低频但关键的路径（出事时才会用到的那个入口）。只数日常路径，会系统性低估最坏情况下的成本。

**怎么用它发言**：把最刺眼的那一行写进 `evidence`，格式为「任务 X：N 次点击 / M 个字段 / K 次跳转 / 等待 1 次，卡在第 2 步的字段含义」。数字是示意口径，不是普适基准，不要跨议题直接比较。

## 3. 出错体验清单

出错是使用体验里最容易被精英视角跳过的一段，因为设计者很少犯错，而第一次用的人几乎必然犯错。

对**每一个**错误场景问四件事：

| 检查项 | 问什么 | 合格 | 不合格 |
|---|---|---|---|
| **说人话** | 提示里有没有内部术语、错误码、英文缩写？能不能被一个不懂这行的人读懂？ | "文件超过了 10MB，请压缩后再上传" | "Error 413: payload too large" |
| **告诉我下一步** | 提示有没有明确说我现在该做什么？ | "请删掉第 3 行的空单元格" | "数据格式有误" |
| **保留我已填内容** | 报错之后，前面填的东西还在不在？要重填多少？ | "保留，只需改第 3 行" | "整个表单清空" |
| **能找到人** | 提示里有没有一个具体的求助入口？ | "点右下角'联系我们'，工作日 2 小时内回复" | "如有疑问请联系管理员"（没有入口） |

**记录格式**（每个错误场景一条）：

```
错误场景：<我做了什么>
我看到的：<提示原文；看不到就写"看不到任何提示">
我下一步会做：<具体动作，写不出就写"不知道该怎么办">
我原来的内容：<还在 / 部分丢失 / 全部丢失 / 无法确认>
卡住程度：<能自己解决 / 要查资料 / 必须找人 / 直接放弃>
```

**纪律**：

- "我看到的"必须写提示原文。写"应该会提示""一般会报错"的，按**未验证**处理，不得作为 claim 论据。
- 确实无法验证的场景（比如没有账号进不去），如实写"无法验证"，并把它登记成一个信息缺口，交给元认知记为 G 编号，而不是猜一个答案填上。
- 三个最常见的错误要覆盖：填错格式、漏填必填、重复提交。只测一个错误场景，说明还没测。

## 4. 放弃点识别方法

放弃不是情绪，是一个**可以被条件化的事件**。找不出放弃点，通常说明测试没做完，而不是方案没问题。

**四步法**：

1. **回放路径**：把第 2 节那张表里最刺眼的一行，按步骤拆成 5–8 个节点，写在一行上。
2. **逐节点问一句**：站在这个节点上，如果下一秒出现最坏情况（要重填、要等、要找人、看不懂），我会继续还是走人？
3. **标出第一个"走人"的节点**，它就是放弃点。**只能有一个**——标出三个说明还没想清楚哪个是致命的。
4. **写出触发条件**，句式固定：

```
如果我在第 <N> 步遇到 <具体障碍>，且还要再 <额外动作>，我就关掉页面去找 <替代方案>。
```

**合格与不合格**：

- 合格：「如果我在第 3 步发现上传失败且要重填整张表，我就直接改用邮件发给对接人。」
- 合格：「如果我要先找主管开通权限才能看到这一屏，我今天就不弄了。」
- 不合格：「如果太麻烦我就不用了。」——没有节点、没有障碍、没有替代方案。
- 不合格：「都不会放弃。」——这不是结论，是没测。

**两条补充判据**：

- **替代方案必须存在且可指名**。说不出替代方案，说明这个方案其实没有竞争者，那么"放弃"的代价要重新算——此时放弃点不成立，应改写为"我会带着不满继续用"。
- **区分第一次与第一百次**。第一次遇到同一个障碍会更想放弃，第一百次已经形成肌肉记忆。放弃点要标注它属于哪种情况，否则改进方向会全部指向一次性成本。

## 5. 常见的五类精英盲区

以下均为**抽象化的工作场景**，用于识别模式，不含任何真实公司、产品或人物。真实议题中须替换为可指名的场景。

**盲区一 · 把内部术语当用户语言**

- 表现：界面、文案、通知里直接使用组织内部叫法（流程代号、系统简称、部门缩写），并假设使用者已经知道。
- 后果：第一次接触者必须先去查这些词，而查的过程不在任何流程图上。
- 识别问法：这个词在**系统之外**的地方出现过吗？如果一个新人从没在别处见过它，它就是内部术语。
- 处理：要么换成人话，要么在原处给一句不超过一行的解释；不接受"用久了就懂了"。

**盲区二 · 把引导当解决方案**

- 表现：遇到"用户不会用"，第一反应是加一个引导页、一段提示、一个浮层。
- 后果：引导是**一次性成本**，而操作路径本身是**每次都要付的成本**。用引导掩盖路径冗长，等于把长期成本换成了短期观感。
- 识别问法：加上引导之后，第 2 节那张表的点击数少了吗？没少，说明只是加了一层说明。
- 处理：先看能不能少一步，再看要不要加引导。两者顺序反了，就会越加越多。

**盲区三 · 把高级功能当核心价值**

- 表现：方案的价值主张建立在一个只有少数人会用的能力上，而多数人要做的那件事被当作"基础功能"草草带过。
- 后果：第一次接触者找不到入口，因为首页被高级功能占满了。
- 识别问法：**最多人每天要做的那一件事**，在这套方案里排第几屏？排不到第一屏，就是一个可质疑的优先级判断。
- 处理：把高频动作与低频高级能力分开摆放，不要用同一个入口承载两种节奏。

**盲区四 · 假设用户会读文档**

- 表现：关键前提写在说明文档、FAQ、更新公告里，界面本身不提示。
- 后果：没读文档的人会在某个节点突然发现规则不对，而这时往往已经做错了一半。
- 识别问法：这条规则如果不读文档就不知道，那么**不读文档的人会在哪一步付代价**？说不出这一步，说明这条规则其实无关紧要。
- 处理：把会改变动作的规则搬到动作发生的位置；纯背景信息可以留在文档里。

**盲区五 · 假设用户只犯一种错**

- 表现：错误处理只覆盖"格式填错"，不覆盖漏填、重复提交、中途离开、用错账号、复制粘贴带空格。
- 后果：唯一被设计过的错误路径体验尚可，其余路径直接把人卡死。
- 识别问法：第 3 节那张表里有几条？只有一条，就是只测了一种错。
- 处理：按"最常见的三种错 + 最贵的一种错"设计提示，而不是按"最容易实现的一种错"。

## 6. 自我警示：平民视角不等于正确

这一节是本手册最重要的部分。**平民视角的产出是一个被忽略的样本，不是一份用户需求说明书。**

- **它只是一个样本，而且是有偏的样本**。样本量为 1，且这个"1"熟悉键盘、看得懂术语、愿意试错——真实的第一次接触者可能一条都不占。本角色的观察能证明"存在这样一个卡点"，**不能**证明"多数人都会卡在这里"。
- **它没有统计效力**。任何写成"用户会觉得""大家都不理解"的句子，如果没有真实数据支撑，都只是把一个人的体感放大成全称判断。正确写法是"我在第 3 步卡住了，原因是我猜不出这个字段的含义"，把范围收回到"我"。
- **它容易被个人偏好污染**。我不习惯某个交互，不等于那个交互有问题——我的习惯本身就是被别的产品训练出来的。每次提出卡点时，都要能给出"不习惯"以外的第二条理由。
- **它看不见实现成本**。提出"这里加个提示""那里加个按钮"是零成本的，落地是有成本的。本角色的建议必须交给承担成本的一方复核，不能因为"对用户好"就跳过这项复核。
- **它对必要复杂度缺乏耐心**。合规、安全、审计、责任认定这些环节，从使用者视角看往往纯粹是多余步骤，但它们有外部强制来源。**看不出价值不等于没有价值**：说不出这条约束的出处时，正确动作是标注"这条我无法评价"，而不是"这条应该删掉"。
- **它会被误用成否决权**。最常见的滥用是：以"用户不会用"为由，否掉所有需要学习的方案。任何有实质能力的东西都需要学习，差别只在学习成本是否与使用频率匹配。本角色的职责是把学习成本**量化并摆出来**，不是替所有人做取舍。
- **它的正确位置是补充，不是裁决**。当平民视角与真实使用数据冲突时，数据优先；当它与专业判断冲突时，先问清楚那条专业判断的外部约束是什么；只有当两者都指向"这一步是多余的"时，这个卡点才具备推动修改的分量。

**一句话总结**：本角色提供的是**一个必须被看见的样本**，而不是**一个必须被服从的结论**。
